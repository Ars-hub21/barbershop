# Пакетная выдача свободных слотов одним запросом (ускорение первой загрузки)

Этот файл — инструкция для того, кто обслуживает Google Apps Script проекта
(тот же скрипт, что стоит за `CONFIG.API_URL` в `js/core/config.js`). Она
описывает **необязательное, но рекомендованное** улучшение на стороне
Google, которое устранит настоящую причину того, что при первом заходе на
сайт свободное время грузится не мгновенно.

**Важно:** ничего во фронтенде (файлы `js/core/api.js`, `js/core/config.js`,
`js/core/global-cache.js`, `js/core/storage.js`) в рамках этой правки не
менялось и меняться не должно — по договорённости эти файлы трогает только
разработчик, который их писал. Сайт и без этой доработки работает корректно
(баг с "Запись закрыта" уже исправлен отдельно, см. ниже), но с текущей
архитектурой первая загрузка объективно медленнее, чем могла бы быть.

---

## 1. В чём сейчас узкое место

При первом заходе на сайт `js/core/global-cache.js` (метод `preloadRange`)
скачивает свободное время на 30 дней вперёд **для каждого мастера
отдельным запросом** к `action=getFreeSlots`. То есть при, например, 5
мастерах это 5 × 30 = **150 параллельных HTTP-запросов** к одному и тому же
Google Apps Script веб-приложению одновременно.

У Apps Script веб-приложений есть ограничение на количество **одновременных**
выполнений скрипта (для большинства аккаунтов это низкие десятки). Когда
запросов одновременно намного больше этого лимита, часть из них не
выполняется параллельно, а встаёт в очередь и ждёт освобождения "слота
исполнения" — из-за этого первая загрузка сайта ощущается медленной,
особенно на телефоне и особенно если мастеров много.

Отдельно: до недавнего исправления в `global-cache.js` была ошибка при
формировании ключей дат в кэше (не то чтобы отправлялось на бэкенд —
просто локально в браузере даты сохранялись под неправильным ключом), из-за
которой свободное время на экране почти всегда выглядело пустым/"Запись
закрыта", даже когда сервер уже успешно ответил. Эта часть уже исправлена
на фронтенде и **не требует** никаких действий на стороне Google — просто
поясняю, чтобы не путать с описанной ниже оптимизацией количества запросов,
которая действительно требует правки на бэкенде.

---

## 2. Что предлагается добавить

Новое действие `getFreeSlotsBatch`, которое одним запросом отдаёт свободное
время сразу по **всем мастерам** за **весь диапазон дат** (например, 30
дней вперёд), вместо одного мастера/одной даты за раз.

### Формат запроса (GET, как и обычный `getFreeSlots`)

```
GET {API_URL}?action=getFreeSlotsBatch&startOffset=0&endOffset=30&duration=15
```

Где `startOffset`/`endOffset` — смещение в днях от сегодняшней даты (то же,
что использует `GlobalCache.preloadRange(startOffset, endOffset)` во
фронтенде), `duration` — можно игнорировать на бэкенде и всегда отдавать
слоты с шагом `SLOT_INTERVAL` (сейчас 15 минут) — фильтрацию по нужной
длительности услуги фронтенд и так делает сам на своей стороне
(`filterSlotsByDuration` в `global-cache.js`).

### Формат ответа — **обязательно** такая форма, фронтенд ждёт именно её

```json
{
  "success": true,
  "slots": {
    "Дени": {
      "2026-09-07": ["10:00", "10:15", "11:00"],
      "2026-09-08": ["10:00", "10:15"]
    },
    "Бауди": {
      "2026-09-07": ["12:00", "12:15"],
      "2026-09-08": []
    }
  }
}
```

То есть `slots` — объект по именам мастеров (те же имена, что в листе
"Мастера"/`js/data/masters.js`), а внутри каждого — объект по датам
`"YYYY-MM-DD"` со списком свободных времён. Эта структура специально
подобрана так, чтобы **один в один** совпадать с тем, как
`GlobalCache.slots` уже хранит данные внутри себя — то есть если бэкенд
начнёт отдавать именно такой ответ, оптимизацию во фронтенде (заменить 150
запросов одним и напрямую присвоить результат в `GlobalCache.slots`)
можно будет сделать буквально в несколько строк внутри `preloadRange`.

### Пример реализации в Apps Script (добавить в диспетчер `doGet(e)`)

```javascript
} else if (action === 'getFreeSlotsBatch') {
  result = getFreeSlotsBatch(
    parseInt(e.parameter.startOffset, 10) || 0,
    parseInt(e.parameter.endOffset, 10) || 30
  );
}
```

```javascript
function getFreeSlotsBatch(startOffset, endOffset) {
  var mastersList = getMastersList(); // или как у вас называется существующая функция получения списка имён мастеров
  var result = {};

  var today = new Date();
  for (var i = 0; i < mastersList.length; i++) {
    var masterName = mastersList[i];
    result[masterName] = {};

    for (var d = startOffset; d < endOffset; d++) {
      var date = new Date(today);
      date.setDate(today.getDate() + d);
      var dateStr = Utilities.formatDate(date, Session.getScriptTimeZone(), 'yyyy-MM-dd');

      // Используйте ту же внутреннюю функцию/логику, что уже применяется
      // в обычном getFreeSlots(master, date) — просто вызывайте её в цикле
      // здесь, а не считайте заново. Так гарантированно не разойдётся
      // логика между одиночным и пакетным способом получения слотов.
      result[masterName][dateStr] = getFreeSlotsForMasterAndDate(masterName, dateStr);
    }
  }

  return { success: true, slots: result };
}
```

Ключевое требование: `getFreeSlotsForMasterAndDate(masterName, dateStr)`
должна быть той же самой внутренней функцией, которую уже использует
существующий обработчик `action=getFreeSlots` — просто вызванной в цикле, а
не переписанной заново. Это гарантирует, что результат пакетного и обычного
запроса всегда будет совпадать.

---

## 3. Почему это ускорит загрузку

Вместо 150 отдельных выполнений скрипта (с очередями/лимитом
одновременных запусков) сервер сделает всю ту же работу **внутри одного**
выполнения скрипта, последовательным циклом (это быстро — Apps Script умеет
пробежать пару сотен ячеек таблицы за доли секунды), и вернёт браузеру один
компактный JSON-ответ. Итог: один HTTP round-trip вместо полутора сотен,
без очередей на стороне Apps Script.

---

## 4. После настройки

Как только `action=getFreeSlotsBatch` появится на бэкенде и будет
**опубликован как новое развёртывание** (Deploy → Manage deployments → New
version), сообщите об этом — фронтенд-часть (переключить
`GlobalCache.preloadRange` на один пакетный запрос вместо цикла) сделаю
отдельным точечным изменением. До этого момента сайт продолжит работать
как сейчас — просто первая загрузка списка свободного времени происходит
за счёт большого количества параллельных запросов, а не одного пакетного.
